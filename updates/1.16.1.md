## Anlass

Am 29.08.2026 zeigte die Anwendung keine Veranstaltungen und keine Rennen mehr.
Im Render-Log stand seit dem Start eine einzige Zeile:

```
❌ DB-Start fehlgeschlagen, laufe ohne Persistenz: column "t" does not exist
```

Die Ursachenkette:

1. `db.init()` legt das Schema an. Das letzte Statement ist
   `CREATE INDEX IF NOT EXISTS track_points_id_t ON track_points (tracker_id, t)`.
2. Die Tabelle `track_points` existierte bereits, aber in einem älteren Layout
   ohne Spalte `t`. `CREATE TABLE IF NOT EXISTS` übergeht eine vorhandene
   Tabelle stillschweigend — auch wenn die Spalten nicht passen.
3. Der Index scheiterte an der fehlenden Spalte und warf.
4. `init()`, `loadStateFromDb()` und `ladeSpurAusDb()` lagen in **einem**
   gemeinsamen `try/catch`. Der Fehler aus Stufe 1 sprang direkt in den
   `catch`-Block — `loadStateFromDb()` wurde nie aufgerufen.
5. Der Server startete mit leerem Speicherstand, obwohl Rennen und
   Veranstaltungen unverändert in der Datenbank lagen.

Es wurde also nichts gelöscht. Es wurde nichts geladen.

Der zweite, gefährlichere Teil: `db.enabled` blieb `true`. Die Schreibpfade
liefen weiter — gegen den leeren Speicherstand. `persistRaceMeta()` und
`persistRuntime()` schreiben jeweils die **komplette** Map, nicht einen
einzelnen Eintrag. Der erste Marker- oder Rundenklick hätte die Rundendaten,
Tracker-Namen und Renn-Zuordnungen aller Rennen mit einer leeren Map
überschrieben. Aus einem Anzeigefehler wäre echter Datenverlust geworden.

## Was sich ändert

**1. Jedes Schema-Statement steht für sich (`db.js`)**

Neuer Helfer `ddl(sql, bezeichnung)`: führt ein Statement aus, protokolliert
einen Fehler in `schemaFehler` und läuft weiter. Alle sieben `CREATE`-Aufrufe
in `init()` gehen jetzt darüber. Ein defektes Detail an einer Nebentabelle
kann den Start nicht mehr abbrechen.

**2. Migration der Tabelle `track_points` (`db.js`)**

Vor dem `CREATE` prüft `migrateTrackPoints()` über `information_schema.columns`,
ob die vorhandene Tabelle eine Spalte `t` hat. Fehlt sie, wird die Tabelle
umbenannt:

```sql
ALTER TABLE track_points RENAME TO track_points_alt_<timestamp>
```

Umbenannt statt gelöscht — das ist umkehrbar. Die alte Tabelle kann später von
Hand entfernt werden; Spurpunkte älter als 24 Stunden verwirft der Server
ohnehin. Die Migration läuft genau einmal: beim nächsten Start hat die neue
Tabelle eine Spalte `t`, und die Funktion steigt sofort wieder aus.

**3. Getrennte Startstufen (`server.js`)**

Schema, Zustand und Spur haben je ein eigenes `try/catch`. Scheitert die Spur,
laufen die Rennen trotzdem. Scheitert das Schema, wird der Zustand gar nicht
erst geladen — und der Schreibschutz greift.

**4. Schreibschutz (`db.js`, `server.js`)**

Ist die Datenbank konfiguriert, der Zustand aber nicht ladbar, ruft der Server
`db.setDegraded(true)`. Danach verwirft `q()` jedes `INSERT`, `UPDATE` und
`DELETE` und protokolliert es. Lesende Abfragen laufen weiter, ebenso
Schema-Statements — sonst könnte sich der Server aus einem kaputten Schema nie
selbst befreien.

Der Schutz sitzt bewusst im gemeinsamen Query-Pfad von `db.js` und nicht an den
rund zwanzig Aufrufstellen im Server. So kann keine künftige Schreibstelle ihn
versehentlich umgehen.

Der Rennbetrieb läuft dabei weiter: Rennen anlegen, Gruppen setzen, Anzeigetext
senden — alles funktioniert im Arbeitsspeicher. Nur zurückgeschrieben wird
nichts. Das ist die bewusste Abwägung: im Rennen darf nichts blockieren, aber
vorhandene Daten dürfen auch nicht überbügelt werden.

**5. `/health` zeigt den Zustand (`server.js`)**

```
🚀 Tracking Server läuft – v1.16.1 – DB: ok – Veranstaltungen: 1 – Rennen: 2 – aktiv: keins
```

Im Fehlerfall:

```
… – DB: SCHREIBSCHUTZ – Veranstaltungen: 0 – Rennen: 0 – aktiv: keins –
Schemafehler: track_points_id_t – verworfene Schreibzugriffe: 3
```

Weiterhin reiner Text, damit vorhandene Uptime-Pings unverändert
funktionieren. Ein Fehlstart wie heute war vorher nur im Render-Log sichtbar —
und dort nur, wenn man wusste, wonach man sucht.

## Rollback

Vorherigen Commit deployen. Die umbenannte Tabelle `track_points_alt_<ts>`
stört dabei nicht: v1.16.0 legt `track_points` selbst an. Der ursprüngliche
Fehler wäre damit allerdings wieder da, solange die Alt-Tabelle nicht
umbenannt oder gelöscht ist.

  75 Funktionsnamen in `server.js` unverändert; in `db.js` vier neue

  Datenbank löst keine Migration aus · Betrieb ohne `DATABASE_URL` unverändert

  den Schreibbetrieb wieder her

  2. **exakter Fehlerfall vom 29.08.** mit gefüllter Datenbank → 1 Veranstaltung
     und 2 Rennen geladen, Schemafehler protokolliert, Start läuft durch

     erscheint im Speicher, erreicht die Datenbank aber nicht
